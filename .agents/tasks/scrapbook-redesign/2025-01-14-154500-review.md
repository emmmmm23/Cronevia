# Scrapbook Visual Redesign and Sticker System Integration

Complete implementation of vintage scrapbook visual redesign with interactive sticker system for Cronevia journal editor. The changes transform a beige form into a denim-blue graph-paper notebook with two-page desktop spread, handwritten fonts, and a drag-and-drop sticker system with Supabase persistence.

The scrapbook aesthetic follows the third reference image: denim-blue (#2C4054) graph-paper background, cream (#F5F1E8) notebook pages with center binding shadows, handwritten title (Indie Flower), serif content (Crimson Text), Polaroid-style photos with washi tape, and pastel sparkle decoration. The sticker system provides 12 built-in SVG assets with drag/resize/rotate via Moveable.js, undo/redo history (50 snapshots), keyboard shortcuts, and normalized-coordinate persistence in journal_sticker_placements table.

**Watch for:** (confirmed) Polaroid styling selector mismatch — PhotoUpload component doesn't use class="photo-preview", so `:deep(.photo-preview)` styling won't apply and Polaroid frames won't render. (confirmed) Moveable CSS not imported — Moveable.js selection handles depend on default CSS which is not imported, so resize/rotate handles may not appear. (likely) Database migration deployment status unknown — sticker tables and buckets must exist in hosted Supabase for save/load to work.

**Verdict**: NEEDS_CHANGES

## High-level view

The visual redesign transforms JournalEditorPage.vue with denim-blue graph-paper background (20px grid), two cream pages on desktop with asymmetric binding shadows (inset -4px on left page, +4px on right), single stacked page on mobile, handwritten title font (Indie Flower 2rem), serif content (Crimson Text 1.8 line-height), and Polaroid photo frames that depend on PhotoUpload's internal structure.

The PhotoUpload component renders image previews in generic divs without class="photo-preview", so the scoped CSS rule `.polaroid-container :deep(.photo-preview)` cannot target them. The Polaroid frames, washi tape pseudo-elements, and alternating rotation will not render. This requires either adding class="photo-preview" to PhotoUpload's preview divs or restructuring the Polaroid styling to match PhotoUpload's actual DOM structure.

StickerEditor integration wires state management (stickersDirty ref, handleStickerDirtyChange emits dirty-change), unsaved changes guard (checks both isDirty and stickersDirty), and save handler (calls stickerEditorRef.value?.savePlacements() with error handling). The component is rendered in both desktop right page and mobile layout with :entry-id, :view-mode, :user-id props.

The sticker system orchestrates five components: StickerCanvas with Moveable bindings, StickerTray with 12 SVG thumbnails from /stickers-builtin/, StickerToolbar with layer/rotation/duplicate/delete controls, StickerPlacement rendering individual stickers, and composables for state management. Moveable.js is imported but its CSS is not, so selection handles (resize corners, rotation handle, blue outline) may not render. The Moveable instance is created with draggable, resizable, rotatable, keepRatio, and bounds, but without the CSS the handles are invisible.

Persistence uses normalized coordinates (0-1 range) stored in journal_sticker_placements with foreign keys to sticker_assets and journal_entries. Built-in stickers are upserted into sticker_assets on first save (user_id IS NULL, storage_path = 'heart-01.svg', etc.) and converted from client-side IDs (builtin-heart-01.svg) to database IDs in savePlacements(). Custom uploads are scoped by user ID ({user_id}/{uuid}.{ext}) with signed URLs (1 hour expiry), RLS policies blocking cross-user placement, and ownership verification before delete.

## Polaroid styling selector mismatch

JournalEditorPage.vue wraps PhotoUpload in `<div class="polaroid-container">` (lines 766, 966) and defines scoped CSS:

```css
.polaroid-container :deep(.photo-preview) {
  background: white;
  padding: 12px 12px 48px 12px;
  box-shadow: 0 4px 8px rgba(0,0,0,0.15);
  /* ... */
}

.polaroid-container :deep(.photo-preview:nth-child(odd)) {
  transform: rotate(-2deg);
}

.polaroid-container :deep(.photo-preview:nth-child(even)) {
  transform: rotate(2deg);
}

.polaroid-container :deep(.photo-preview::before) {
  content: '';
  /* washi tape pink gradient */
}
```

PhotoUpload.vue renders image previews in two sections: existing photos (lines 137-158) and new photo previews (lines 161-192). Both use generic divs with classes like `relative aspect-square bg-[#f5ebdd] border border-[#d7c7b3] rounded overflow-hidden group` but never `photo-preview`.

The `:deep()` selector pierces Vue's scoped style boundary, but it still requires the target element to have the class name. Since PhotoUpload doesn't use class="photo-preview", the Polaroid styling won't apply. Photos will render as flat rounded squares with tan background, no white frame, no washi tape, no alternating rotation.

Fix: Add `class="photo-preview"` to the existing photo div (line 139) and new photo preview div (line 164) in PhotoUpload.vue. This requires modifying PhotoUpload.vue which is a shared component (used by journal entries, trips, memories per the file header comment). Ensure the Polaroid styling doesn't break other uses, or scope it more tightly to JournalEditorPage by removing the .polaroid-container wrapper and targeting PhotoUpload's root element with a journal-specific class.

Alternative: Rewrite the Polaroid CSS to use a selector that matches PhotoUpload's actual structure, e.g., `.polaroid-container :deep(.relative.aspect-square)`. This is fragile because it relies on Tailwind utility classes which could change.

## Moveable CSS missing

StickerCanvas.vue imports Moveable (line 9) and creates an instance (lines 64-81) with draggable, resizable, rotatable, keepRatio, and bounds. Moveable's default appearance includes a blue outline, white corner resize handles, and a circular rotation handle. These are styled by moveable/dist/moveable.css which is not imported.

Without the CSS, the Moveable instance still functions (event listeners fire, transform updates work), but all handles are invisible. Users can drag a selected sticker because the entire image is the drag target, but they cannot resize or rotate because the handles are not rendered. The toolbar rotation buttons still work (they directly update the rotation value), but the interactive rotation handle won't appear.

Fix: Add `import 'moveable/dist/moveable.css'` to StickerCanvas.vue's <script setup> block (after the Moveable import on line 9). Alternatively, import it in main.ts or style.css if moveable is used elsewhere. The CSS file is ~20KB and includes handle positioning, outline styles, and rotation handle appearance.

Vite should handle the CSS import correctly (it's a standard ESM import from node_modules). If the import fails, verify that moveable is installed (package.json dependencies) and that Vite's CSS processing is working.

## Database migration and builtin asset seeding

The sticker.service.ts savePlacements() function (lines 313-393) handles builtin stickers specially: for each placement with assetId starting with "builtin-", it checks if a row exists in sticker_assets with user_id IS NULL and storage_path matching the filename. If not, it inserts the row (lines 323-335). This upsert strategy ensures referential integrity without requiring a seed script.

However, this logic runs only when a journal entry is saved. If the journal_sticker_placements table doesn't exist, the save fails before reaching this code. The migration file supabase/migrations/20261012000001_add_sticker_system.sql defines:

- sticker_assets table (id, user_id, storage_path, mime_type, width, height, category, created_at, updated_at)
- journal_sticker_placements table (id, journal_entry_id, sticker_asset_id, x, y, width, rotation, z_index, created_at, updated_at)
- stickers-builtin and stickers-custom storage buckets
- RLS policies on both tables
- Storage policies (stickers-builtin allows SELECT for authenticated; stickers-custom allows ALL for auth.uid() folder)
- Trigger validate_sticker_placement that blocks placing another user's private sticker

The FEAT-001 and FEAT-002 findings state "Build completed successfully with no TypeScript errors" but do not confirm database migration deployment. The INTEGRATION-VERIFICATION-REPORT.md (line 397) states "Cannot Verify Without Browser" and "deployment status is unknown without database access."

Without the migration applied, the first save attempt will fail with a Supabase error (e.g., "relation 'journal_sticker_placements' does not exist" or "Storage bucket 'stickers-custom' does not exist"). The handleSave error handler in JournalEditorPage.vue (line 402-404) catches this and sets saveError to "Entry saved, but sticker placements failed to save. Please try saving again." This is a reasonable error message for transient failures, but for a missing migration, retrying won't help.

To verify: Run `supabase db diff` (requires Supabase CLI and linked project) or check the Supabase dashboard -> Database -> Tables tab for sticker_assets and journal_sticker_placements. If missing, apply the migration via `supabase db push` or SQL editor. The migration is not reversible without a down migration, so back up production data first if applying manually.

## Undo/redo and keyboard shortcuts

useStickerEditor.ts maintains history state: history ref (array of StickerLayout snapshots), historyIndex ref (current position), MAX_HISTORY = 50. StickerLayout is { version: 1, surfaces: [{ id: string, stickers: StickerInstance[] }] }. The surfaces array is designed to support multi-surface layouts (e.g., two-page spread with separate sticker layers per page), but currently only one surface ("page-1") is used.

createSnapshot() copies placements.value into a StickerLayout. saveSnapshot() appends the snapshot to history, removes future history if historyIndex < length - 1 (branching after undo), and shifts old snapshots if exceeding MAX_HISTORY. undo() and redo() decrement/increment historyIndex and call restoreSnapshot(), which replaces placements.value with the snapshot's stickers.

StickerEditor.vue registers a keydown listener on window (not shown in limited read but confirmed in FEAT-002 verification findings). Keyboard shortcuts: Delete (deleteSticker if selectedId), Escape (clearSelection), Ctrl+Z (undo if canUndo), Ctrl+Shift+Z (redo if canRedo), arrow keys (nudge selected sticker by 1px via updatePlacement). The listener is removed on onBeforeUnmount.

The toolbar's Undo/Redo buttons are disabled when !canUndo or !canRedo. Duplicate creates a copy with +10px offset in normalized coordinates. Rotate Left/Right adjust rotation by ±15 degrees. Bring Forward/Send Backward adjust zIndex by ±1. Delete removes the sticker. All toolbar actions call editor.saveSnapshot() to commit to history.

Moveable events (dragEnd, resizeEnd, rotateEnd) emit save-snapshot from StickerCanvas, which StickerEditor listens to and calls editor.saveSnapshot(). This ensures every user interaction creates a history entry.

## Normalized coordinates and responsive layout

Sticker positions are stored as normalized coordinates (0.0 to 1.0 range) relative to canvas dimensions. useStickerEditor.ts sets canvasWidth and canvasHeight refs (default 800x1000, updated by StickerEditor on mount from canvasRef.value.offsetWidth/offsetHeight). When adding a sticker, the initial position is { x: 0.5, y: 0.5, width: 0.15 } (centered, 15% of canvas width).

When dragging/resizing, StickerCanvas emits normalized values (e.g., x = transformMatrix.m41 / canvasRect.width). The normalization clamps x/y/width to [0, 1] range (Math.max(0, Math.min(1, value))) after dragEnd/resizeEnd to ensure no sticker is positioned outside the 0-1 coordinate space.

StickerPlacement.vue multiplies x/y/width by 100% in its style binding (left: x * 100%, top: y * 100%, width: width * 100%). The transform: translateX(-50%) translateY(-50%) centers the sticker on its coordinate, so (0.5, 0.5) is the canvas center.

The bounds constraint in Moveable (left: 0, top: 0, right: canvasRect.width, bottom: canvasRect.height) prevents stickers from being dragged outside the visible canvas. However, the bounds are set once when Moveable is initialized (line 71-77 in StickerCanvas.vue). If the canvas is resized (e.g., window resize, orientation change), the bounds are stale. This is acceptable for the current implementation since canvasRect is captured from props.canvasEl.getBoundingClientRect() inside the watch callback, so it updates when canvasEl changes. However, window resize doesn't re-trigger the watch unless props.canvasEl reference changes.

The normalized coordinates mean stickers stay in the same relative position if the canvas is resized. For example, a sticker at (0.5, 0.5) with width 0.15 is always centered and 15% of canvas width, whether the canvas is 800px or 400px. This is critical for mobile vs desktop consistency.

## Persistence transaction and error handling

savePlacements() in sticker.service.ts (lines 313-393) performs a transaction: DELETE all existing placements for the entry, then INSERT new rows. This upsert strategy is simpler than diffing and updating individual placements. The DELETE happens before INSERT (line 327), so if INSERT fails, the entry is left with no placements. This is a data loss scenario if the save fails after DELETE.

Supabase doesn't support explicit SQL transactions from the client library (it's auto-committed per request). To make this atomic, the DELETE and INSERT should be wrapped in a Postgres function or the logic should be changed to use UPSERT (INSERT ... ON CONFLICT DO UPDATE). The current implementation is vulnerable to partial failure.

However, the check() function (lines 13-17) throws immediately on error, so if DELETE fails, INSERT never runs. If DELETE succeeds but INSERT fails, the placements are lost and the error is thrown. The error propagates to JournalEditorPage handleSave (line 400-404), which catches it and sets saveError to "Entry saved, but sticker placements failed to save. Please try saving again." The error message doesn't mention that existing placements were deleted, which could confuse the user if they had saved placements before.

Better error handling: wrap DELETE+INSERT in a Postgres function that runs in a transaction, or change the strategy to INSERT with ON CONFLICT (id) DO UPDATE and DELETE only placements not in the new set. Alternatively, store placements in a JSONB column on journal_entries (the migration adds sticker_layout JSONB, line 313 of migration file, but the code doesn't use it).
