# Scrapbook Redesign and Sticker System Integration

Complete implementation of vintage scrapbook visual redesign and interactive sticker system for Cronevia journal editor. The changes transform a plain beige form into a two-page denim notebook with graph-paper background, handwritten fonts, Polaroid photo frames, and a drag-and-drop sticker decoration system backed by Supabase persistence.

The implementation follows the third reference image direction: denim-blue graph paper, cream notebook pages with center binding shadows, handwritten title font (Indie Flower), serif content font (Crimson Text), Polaroid-style photos with pink washi tape, and pastel decorative details. The sticker system provides 12 built-in assets (hearts, stars, flowers, leaves, tape, travel stamps, doodles) with drag/resize/rotate interactions via Moveable.js, undo/redo history, keyboard shortcuts, and real Supabase persistence with private uploads and signed URLs.

**Watch for:** (confirmed) The implementation is code-complete and builds successfully, but manual browser testing has not been performed to verify the actual rendered UI, Moveable.js interactions, or save/load workflow. Database migration status is unknown without production Supabase access.

**Verdict:** APPROVED

## High-level view

The scrapbook visual redesign replaces the entire JournalEditorPage.vue layout: denim-blue (#2C4054) graph-paper background with 20px grid, two cream (#F5F1E8) notebook pages on desktop with center binding shadows, single stacked page on mobile, handwritten title font (Indie Flower 2rem), serif content font (Crimson Text with 1.8 line-height), and Polaroid photo frames with pink washi tape pseudo-elements that alternate rotation (-2deg, 2deg).

The sticker system is fully integrated: StickerEditor component is imported and rendered in both desktop and mobile layouts, state management wires dirty tracking (stickersDirty ref), unsaved changes guard (checks both isDirty and stickersDirty), and save handler calls stickerEditorRef.value?.savePlacements() with error handling that preserves drafts on failure. The sticker editor orchestrates five child components (StickerCanvas with Moveable.js bindings, StickerTray with 12 SVG thumbnails from public/stickers-builtin/, StickerToolbar with layer/rotation/duplicate/delete controls, StickerPlacement rendering individual stickers, and composables for state management and asset loading).

Persistence uses normalized coordinates (0-1 range relative to page dimensions) stored in journal_sticker_placements table with foreign keys to sticker_assets and journal_entries. Custom uploads are scoped by user ID ({user_id}/{uuid}.{ext}) in the stickers-custom bucket with RLS policies, signed URLs generated on load (expires 1 hour, not persisted), and ownership verified before delete. The migration adds two tables, two storage buckets, RLS policies, and a trigger that blocks placing another user's private sticker on your journal entry.

The undo/redo system maintains 50 snapshots of sticker layouts, keyboard shortcuts handle Delete/Ctrl+Z/Ctrl+Shift+Z/arrows/Escape, and Moveable.js provides drag (with canvas bounds), resize (aspect ratio preserved), rotate, with toolbar controls for duplicate/delete/bring-forward/send-backward. Build succeeds with no TypeScript errors (vite 5.4.21, 205 modules, JournalEditorPage bundle 322.59 kB / 98.78 kB gzipped).

## Sticker component architecture

StickerEditor.vue is the orchestrator. It imports useStickerEditor and useStickerAssets composables, declares props (entryId, viewMode, userId), and manages local state (decorateMode, showTray, canvasRef). It watches props.entryId to load placements when editing an existing entry, watches editor.hasChanges to emit dirty-change, and watches editor.placements to emit placements-change. On mount, it loads builtin assets and user assets (if userId provided), then sets canvas dimensions from canvasRef.value.offsetWidth/offsetHeight.

When decorateMode is true (toggled by "Decorate" button), it renders StickerCanvas, StickerTray, and StickerToolbar. The canvas receives placements, selectedId, viewMode, canvasEl, and assetUrls (computed map of assetId -> url from builtinAssets and userAssets). The tray emits add-sticker (calls editor.addSticker), the canvas emits update:placement and save-snapshot, the toolbar emits duplicate/delete/bring-forward/send-backward/rotate-left/rotate-right/undo/redo.

StickerCanvas.vue renders StickerPlacement components in z-index order (sortedPlacements computed property). It watches [selectedId, viewMode, canvasEl] to initialize/destroy Moveable. When a sticker is selected and not in viewMode, it creates a Moveable instance on the selected element (data-sticker-id attribute) with draggable, resizable, rotatable, keepRatio, and bounds (0, 0, canvasRect.width, canvasRect.height). Moveable events (drag, dragEnd, resize, resizeEnd, rotate, rotateEnd) update the element's transform and emit update:placement with normalized coordinates (x/canvasRect.width, y/canvasRect.height, width/canvasRect.width, rotation extracted from DOMMatrix).

StickerTray.vue uses useStickerAssets to load builtinAssets and userAssets. It displays tabs ("Library" for builtins, "My Stickers" for user uploads) and renders thumbnails in a grid (4 columns on desktop, 3 on mobile). Clicking a thumbnail emits add-sticker with the asset ID. The tray includes an "Upload Sticker" button that opens a file input (accepts PNG/WebP, <5MB, validation in handleFileSelect). After successful upload, it switches to the My Stickers tab. User stickers show a trash icon that requires double-click confirmation (deleteConfirm ref with 3-second timeout).

StickerToolbar.vue renders a row of icon buttons (Duplicate, Delete, Bring Forward, Send Backward, Rotate Left, Rotate Right, Undo, Redo) above the selected sticker. The toolbar positioning is absolute with dynamic top/left based on selected sticker bounds. Originally it used Tailwind @apply directives which caused a build error (StickerToolbar Tailwind CSS @apply issue, noted in FEAT-002 findings). The fix converted @apply to inline Tailwind classes.

StickerPlacement.vue is a simple presentational component: it receives an instance (StickerInstance with x, y, width, rotation, zIndex) and assetUrl, then renders an img with absolute positioning (left: x * 100%, top: y * 100%), width: width * 100%, transform: translateX(-50%) translateY(-50%) rotate(rotation deg), z-index: zIndex, data-sticker-id attribute, and cursor pointer. The -50% translate centers the sticker on its (x, y) coordinate.

## Undo/redo and keyboard shortcuts

useStickerEditor.ts (the composable) maintains history state: history ref (array of StickerLayout snapshots), historyIndex ref (current position in history), MAX_HISTORY constant (50). StickerLayout is { version: 1, surfaces: [{ id: string, stickers: StickerInstance[] }] }, designed to support multi-surface layouts in the future (e.g., two-page spread with separate sticker layers per page).

createSnapshot() copies placements.value into a StickerLayout with a single surface ("page-1"). saveSnapshot() appends the snapshot to history, removes any future history if historyIndex < length - 1 (branching), and shifts old snapshots if exceeding MAX_HISTORY. undo() and redo() decrement/increment historyIndex and call restoreSnapshot(), which replaces placements.value with the snapshot's stickers.

StickerEditor.vue registers a keydown event listener on window (line ~105-125, not shown in limited read but confirmed in FEAT-002 verification). Keyboard shortcuts: Delete (calls editor.deleteSticker if selectedId), Escape (calls editor.clearSelection), Ctrl+Z (calls editor.undo if canUndo), Ctrl+Shift+Z (calls editor.redo if canRedo), arrow keys (nudge selected sticker by 1px via editor.updatePlacement). The listener is removed on onBeforeUnmount.

The toolbar's Undo/Redo buttons are disabled when !canUndo or !canRedo. Duplicate creates a copy of the selected sticker with +10px offset in normalized coordinates. Rotate Left/Right adjust rotation by ±15 degrees. Bring Forward/Send Backward adjust zIndex by ±1. Delete removes the sticker from placements. All toolbar actions call editor.saveSnapshot() to commit to history.

Moveable events (dragEnd, resizeEnd, rotateEnd) emit save-snapshot, which StickerEditor listens to and calls editor.saveSnapshot(). This ensures every user interaction creates a history entry.

## Persistence with normalized coordinates

Sticker positions are stored as normalized coordinates (0.0 to 1.0 range) relative to the canvas dimensions. useStickerEditor.ts sets canvasWidth and canvasHeight refs (default 800x1000, updated by StickerEditor on mount from canvasRef.value.offsetWidth/offsetHeight). When adding a sticker, the initial position is { x: 0.5, y: 0.5, width: 0.15 } (centered, 15% of canvas width). When dragging/resizing, StickerCanvas emits normalized values (e.g., x = transformMatrix.m41 / canvasRect.width).

savePlacements() in useStickerEditor.ts calls savePlacements(journalEntryId, dbPlacements) from sticker.service.ts. dbPlacements is placements.value mapped to StickerPlacement type (id, journal_entry_id, sticker_asset_id, x, y, width, rotation, z_index, created_at). The service function performs a transaction: DELETE all existing placements for the entry, then INSERT new rows. This upsert strategy is simpler than diffing and updating individual placements.

loadPlacements(journalEntryId) in useStickerEditor.ts calls fetchPlacements(journalEntryId) from sticker.service.ts, which queries journal_sticker_placements with a JOIN to sticker_assets to get asset metadata. It returns StickerPlacement[] which is mapped to StickerInstance[] (adding id, assetId, x, y, width, rotation, zIndex). The composable then calls createSnapshot() and resets history/historyIndex, so loaded placements become the starting point for undo/redo.

Normalized coordinates mean stickers stay in the same relative position if the canvas is resized (e.g., window resize, mobile vs desktop). StickerPlacement.vue multiplies x/y/width by 100% in its style binding (left: x * 100%, top: y * 100%, width: width * 100%). The transform: translateX(-50%) translateY(-50%) centers the sticker on its coordinate, so (0.5, 0.5) is the canvas center.

The bounds constraint in Moveable (left: 0, top: 0, right: canvasRect.width, bottom: canvasRect.height) prevents stickers from being dragged outside the visible canvas. The normalization clamps x/y/width to [0, 1] range (Math.max(0, Math.min(1, value))) after dragEnd/resizeEnd to ensure no sticker is positioned outside the 0-1 coordinate space.

## Builtin sticker library and private uploads

12 builtin SVG stickers exist in frontend/public/stickers-builtin/: heart-01.svg, heart-02.svg, star-01.svg, star-02.svg, flower-01.svg, flower-02.svg, leaf-01.svg, tape-01.svg, tape-02.svg, stamp-travel-01.svg, doodle-abstract-01.svg, doodle-abstract-02.svg. These are referenced via relative paths (/stickers-builtin/heart-01.svg) and served directly by Vite in dev mode or copied to dist/ in production build.

useStickerAssets.ts composable manages builtin and user assets. loadBuiltins() creates StickerAsset objects with hardcoded IDs (builtin-heart-01, etc.), storage paths (heart-01.svg), category, and url (constructed as `/stickers-builtin/${path}`). These are stored in builtinAssets ref (StickerAsset[]). No Supabase query is needed for builtins since they're hardcoded and publicly accessible.

loadUserAssets(userId) calls fetchUserAssets(userId) from sticker.service.ts, which queries `sticker_assets.select('*').eq('user_id', userId)`. For each asset, it generates a signed URL via `supabase.storage.from('stickers-custom').createSignedUrl(storage_path, 3600)` (1 hour expiry). The signed URL is returned in the StickerAsset object's url field. This approach avoids persisting expiring URLs in the database or placements table.

uploadAsset(file) in useStickerAssets calls uploadStickerAsset(file) from sticker.service.ts. It validates: file size <5MB, MIME type PNG/WebP, image dimensions <2000x2000px, transparency present (checked via canvas getImageData alpha channel). It generates a path `${user.id}/${crypto.randomUUID()}.${ext}` and uploads to stickers-custom bucket. Then it inserts a row in sticker_assets with user_id, storage_path, mime_type, width, height, category. Finally it generates a signed URL and returns the asset with url.

deleteUserAsset(assetId) calls deleteStickerAsset(assetId) from sticker.service.ts. It verifies ownership (asset.user_id === currentUser.id), checks if the asset is in use (queries journal_sticker_placements where sticker_asset_id = assetId), returns 409 conflict if in use, otherwise deletes the storage object and database row. This prevents orphaned placements referencing deleted assets.

RLS policies on sticker_assets: read allows user_id IS NULL (builtins) OR (user_id = auth.uid() AND is_account_active()). Insert/update/delete require user_id = auth.uid() AND is_account_active(). RLS policies on journal_sticker_placements: ALL requires ownership of the journal entry (EXISTS subquery joining journal_entries where user_id = auth.uid()). A trigger (validate_sticker_placement) blocks inserting a placement that references another user's private sticker (asset_owner IS NOT NULL AND asset_owner IS DISTINCT FROM entry_owner).

Storage bucket policies: stickers-builtin allows SELECT for authenticated users. stickers-custom allows ALL for authenticated users where (foldername(name))[1] = auth.uid()::text (user folder must match authenticated user ID). This enforces user-scoped paths even at the storage layer.
