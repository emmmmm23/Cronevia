# Password recovery isolation

The existing `/forgot-password`, `/reset-password`, and `/login` URLs are preserved. Reset emails request the exact current-origin `/reset-password` callback. A successful recovery callback that Supabase sends to Site URL instead is recognized by its recovery type and moved to `/reset-password` before the main Auth client or router processes its credentials. Signup and journal-invitation callbacks keep their existing handling.

Recovery uses a separate Supabase client with in-memory credentials, no persistent browser storage, no session detection from URL, and no cross-tab account channel. It never supplies the normal account store with a signed-in user or loads that account's private profile. Previously persisted sessions whose signed method explicitly identifies recovery are quarantined into the same flow. Ordinary sign-in sessions cannot authorize the reset form.

Supabase's implicit `/verify` flow issues email-recovery sessions with the `otp` method, rather than `recovery`; the project's recent Auth method records and [upstream implementation](https://github.com/supabase/auth/blob/master/internal/api/verify.go) confirm that behavior. The original strict recovery-only classifier incorrectly rejected those fresh links. The corrected callback accepts server-verified OTP sessions only within the captured recovery flow, then registers the signed session ID for recovery-only database access before making the reset form available. Both object and RFC string AMR formats are handled. Normal password sessions mislabeled in a URL are rejected, and normal OTP signup/sign-in callbacks are preserved. Transient verification failures offer an in-memory retry instead of falsely reporting an expired link; a verified one-time email token is not consumed twice on retry.

The Auth server verifies the recovery session and its user identity. Password submission rechecks that identity and uses only the isolated client, so a different account previously signed into the browser cannot become the reset target. Existing verified TOTP factors still require a valid authenticator code. Success discards recovery state and offers sign-in with the new password. Cancellation also discards recovery state. A page reload requires a new reset email because recovery credentials are intentionally not persisted.

The database migrations `supabase/migrations/20261029110110_password_recovery_isolation.sql` and `supabase/migrations/20261029124656_email_otp_recovery_sessions.sql` have been applied to project `lrgxrfyzakehsnifypmd`. The latter adds a private, RLS-protected registry of recovery session IDs and a narrow authenticated registration function. Registration checks the signed user/session IDs against `auth.sessions`; it cannot target another account and never grants data access. The account guard denies registered sessions and explicit recovery methods, including after MFA or refresh. OTP access also requires a live Auth session, so logout and cascading registry cleanup cannot restore access to an old OTP JWT. Other normal sessions of the same account stay unaffected. Existing restrictive policies and guarded RPCs thereby keep profiles, journals, sharing, trips, trackers, private media and administrator operations closed for the registered recovery session. Authorization never uses editable user metadata. Auth can still change the password. Schema marker: `20261029.3`.

After changing the password, the isolated client attempts global sign-out to revoke refresh sessions. Previously issued access tokens from ordinary account sessions can remain valid until expiry; this is not a claim of immediate revocation of already issued JWTs. Recovery tokens remain denied app-data access by the database guard.

Hosted Auth should retain existing redirect URLs and explicitly allow `https://cronevia.vercel.app/reset-password`. The equivalent local URLs are included in `supabase/config.toml`; local configuration does not overwrite hosted settings. The fallback handling above supports recovery callbacks sent to the existing Site URL. Existing email templates should continue to use `{{ .ConfirmationURL }}`. See [Supabase password recovery](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [redirect URL configuration](https://supabase.com/docs/guides/auth/redirect-urls), and [signed authentication-method claims](https://supabase.com/docs/guides/auth/jwt-fields).

The OTP correction is verified with 12 recovery unit checks, 18 distinct account-security browser scenarios, full PostgreSQL/PGlite feature regressions, and hosted schema/privilege checks. Tests cover actual OTP and string-AMR formats, account/session binding, MFA and refresh, normal-session preservation, denial after logout, callback retries and rejected password-sign-in tokens. Browser tests intercept Auth requests and never send real emails or change hosted passwords. Actual email delivery and password changes are left to the account holder. The security advisor adds expected notices for the private deny-by-default registry and its authenticated definer RPC; the latter is deliberately callable only to restrict the caller's own verified session. See [definer-function review guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). No ERROR-level finding was introduced. Existing findings and their remediation links remain recorded in `docs/shared-journals.md`.
